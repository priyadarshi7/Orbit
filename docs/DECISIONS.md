# Decision log

Every design decision for Orbit, in the order it was made, with the reason and what was rejected.
`DESIGN.md` is the one-page summary for reviewers; this file is the full record.

**Status key:** **Decided** (you confirmed it) · **Adopted** (I proposed it and you did not object; confirm or overturn) · **Open** (not yet decided).

Last updated: 2026-11-14 (after the first end-to-end build).

## A. Goal and principles

| # | Decision | Status | Why | Rejected |
|---|---|---|---|---|
| A1 | Build a **general** best-in-class web-search chat agent. The three sample questions are examples, not the target. | Decided | The test set is unseen. Overfitting to the samples would fail on everything else. | A design centred on dated recall and "has it changed?" (first draft) |
| A2 | Thesis: **the model decides, the harness guarantees.** The model owns judgment (search or not, which queries, when to stop). ## B. Agent core

| # | Decision | Status | Why | Rejected |
|---|---|---|---|---|
| B1 | **One tool: `web_search`.** | Decided (brief) | The brief says one tool. | A second memory/recall tool |
| B2 | **Model-driven agent loop**, no intent classifier or planner call before it. Hard caps on rounds (≤4), queries per round and total tokens. | Adopted | A router adds a round trip before the first token and is wrong on exactly the questions nobody anticipated. | Router/planner LLM; multi-agent frameworks; LangChain |
| B3 | `web_search` is a **retrieval pipeline**: parallel fan-out, dedupe, read pages (`depth: read`), chunk and rank passages, token-capped evidence pack with id, domain and publish date. Partial results on timeout. | Adopted | Most of the answer quality comes from retrieval, not the model. Reading pages beats snippets. | Snippet-only search; provider-hosted web search (no control over fan-out, reading, caching, ranking) |
| B4 | **Grounding gate in code**: citations must resolve to real evidence ids (others dropped); relative dates become absolute; conflicting sources are named; missing evidence is stated. | Adopted | Verified in code, not trusted to the prompt. | Trusting the model's citations |
| B5 | Fetched page text is **untrusted data**, wrapped so it cannot give instructions. | Adopted | Prompt-injection defence. Has a dedicated eval category. | None considered |
| B6 | Deadlines propagate from turn to tool call; on timeout the agent answers with what it has and says what it could not check. Degrade, never fail. | Adopted | Latency and reliability. | Hard failures |

## C. Memory

| # | Decision | Status | Why | Rejected |
|---|---|---|---|---|
| C1 | Memory is **context assembled by code before the model runs**, not a tool. | Adopted | Respects the one-tool rule and saves a round trip. Known cost: the model cannot fetch a past chat the harness missed. If evals show misses, add a `recall` tool. | Memory as a second tool |
| C2 | Three stores in one SQLite file: **episodic** (turns, summaries, keywords), **profile** (durable user facts), **claims** (atomic, dated, sourced facts, each linked to the claim it supersedes). Claims are one store among three, not the core. | Adopted | Episodic and profile serve any conversation; claims make "has X changed?" a diff instead of a guess. | Transcript-only memory (cannot be diffed); claims as the centre of the design |
| C3 | **Exact dates are SQL keys**; dates in the message are resolved with chrono-node in the user's timezone; topic match uses FTS5 over model-written summaries and keywords. | Adopted | Dates are exact, so embeddings add fuzz. FTS5 over summaries covers paraphrase. | Vector DB as primary memory (revisit as a second index later) |
| C4 | If nothing matches, the context says so and the agent says so, naming nearest dates. It never invents a past conversation. | Adopted | A fresh clone has no history; reviewers will hit this first. | Silent fallback |
| C5 | **Memory writer runs after the response** (async, off the hot path) and reads jobs from an **outbox table**: idempotent per turn, survives a crash. | Adopted | Zero added latency to the answer; no lost writes. | Writing memory inline; fire-and-forget without persistence |
| C6 | A `seed` script loads a dated demo history so memory features are demonstrable within a minute of cloning. | Adopted | Without it, memory looks empty to a reviewer. | None |

| # | Decision | Status | Why | Rejected |
|---|---|---|---|---|
| D1 | **No Claude / Anthropic models** in the agent. | Decided | Your instruction. No reason was given and none is assumed. | Everything earlier that named Claude models, pricing or Anthropic features (all withdrawn) |

| D9 | Tool-call validity and streaming of tool calls are tested per model in the benchmark. | Adopted | They differ between vendors and the loop depends on them. | Assuming parity |

## I. Decisions made while building

| # | Decision | Status | Why | Rejected |
|---|---|---|---|---|
| I1 | **Recall is gated.** Dates in the message always trigger an exact SQL lookup; FTS5 topic recall runs only when the message is dated or uses a recall cue ("earlier", "last time", "changed", "since", "we shortlisted"…). The profile and a six-line recent-chat timeline are always included. | Adopted | Injecting stored chats into every turn adds tokens and distracts the model on unrelated questions. It is a regex heuristic: if the eval shows missed recalls, widen the cues or add a `recall` tool. | Always-on topic recall |
| I2 | A year-less date in the future ("20 December" asked in November) means last year's; a weekday in the future means last week's. Same-day and future dates are ignored. | Adopted | Recall questions are about the past. Covered by tests, including a timezone edge case. | Treating all parsed dates literally |
| I3 | **Answer recovery.** The last step forbids tool calls (`toolChoice: none`, which keeps the cached prefix). If a model ignores that, or dies after searching, one tool-free call answers from the gathered evidence. | Adopted | Found by a test: the SDK throws when a model calls a tool under `none`, which would have cost the user an answer despite good evidence. Weaker or local models do this. | Showing an error |
| I4 | Text a model writes *before* a tool call is a preamble: streamed live, then discarded with a `reset` event once the step turns out to be a tool call. | Adopted | Keeps first-token latency (no buffering) without leaving "Let me search…" in the answer. | Buffering every step until it finishes |
| I5 | The **answer fallback model** is used only if the primary fails before producing any text (rate limit, outage). | Adopted | Free tiers rate-limit; a visible failure in front of a reviewer is the worst case. | Retrying the same model |
| I6 | If memory extraction fails after retries, a **minimal episode** (user message, keywords) is still stored. | Adopted | The turn stays findable by date and keyword even when the small model is down or returns bad JSON. | Dropping the memory |
| I7 | The grounding gate **drops** unresolved citations and **lints** undated relative-time language and uncited answers; it does not rewrite dates. Relative-to-absolute dates are a prompt rule checked by the eval. | Adopted | Rewriting dates in code needs the model's intent; dropping fake citations does not. `DESIGN.md` was corrected to say this. | Claiming the gate enforces dates |
| I8 | Eval cases check **behaviour** (searched or not, citations, regexes) for facts that change over time, and exact values only for stable facts. | Adopted | A fixed expected "latest version" would be wrong next month. | Hard-coded answers for live facts |
| I9 | Prompt-injection cases use **fixed evidence** (not live search) so they are deterministic. | Adopted | A live page cannot be relied on to contain an attack. | Live-only injection tests |
| I10 | The UI has **Stop** and **Retry** (on error). No separate regenerate. | Adopted | Regenerate would append a duplicate turn to the stored conversation and to memory. | Regenerate button |
| I11 | The demo history (`npm run seed`) is **illustrative** and labelled so. Its prices are not a statement of real pricing. | Adopted | The agent will correctly report them as changed when live pages differ. | Presenting demo values as real |
| I12 | Evidence is budgeted **per call (2,000 tokens) and per turn (3,500)**, output capped at 1,500, up to 4 rounds. All tunable in `.env`. | Adopted (revised) | First live run: Groq rejected a request of 9,053 tokens against an 8,000 TPM limit. Measured cause: every search round adds its evidence to every later call, and the provider also counts reserved output. The old defaults (3,500 per call, no per-turn cap, 2,000 output) let two rounds exceed 8k. Measured after the fix: calls of 915, 2,831 and 4,349 input tokens. | Per-call budget only |
| I13 | No thinking-budget or effort options are set. Per-model provider options belong in the model config once the benchmark shows which models need them. | Adopted | Those knobs differ per vendor; guessing them before measuring is how config rots. | Hard-coded provider options |
| I14 | `npm run dev` runs the API with `node --watch --import tsx`, not `tsx watch`. | Adopted | `tsx watch` never started the server under `concurrently` on the author's Windows machine; Node's built-in watch did. | `tsx watch` |
| I15 | Vitest is pinned to the `vmThreads` pool. | Adopted | The default pools failed with "failed to find the current suite" on the author's Windows/Node 24 machine, even for a trivial test; `vmThreads` passes all 40. Root cause not found. Revisit if it misbehaves elsewhere. | Default pool |
| I16 | Starting model ids come from `npm run models` against the real keys: answer `groq:openai/gpt-oss-120b`, fallback `google:gemini-2.5-flash`, background `google:gemini-3.1-flash-lite`, judge `google:gemini-2.5-flash`. These are starting points for the benchmark, not winners. | Adopted | My first guesses (`llama-3.3-70b-versatile`, `llama-3.1-8b-instant`) were not available to your Groq key, so the first live run silently fell back to Gemini. | Guessing ids without listing them |
| I17 | **A date is a recall request only if the message also refers back to a chat** (asked, told, discussed, "what did we…", "since", "last time"…). "I was born on 30 April 2005" is a statement, not a lookup. | Adopted | Found in the first live run: the birth date triggered `NO RECORD` and the agent replied "I have no record of any conversation on 30 April 2005". Two new tests pin this. | Treating every parsed date as a lookup |
| I18 | **Cited-but-never-searched is a certain failure.** If the answer contains `[n]` citations but nothing was retrieved, the turn is re-run once with the search tool required (`toolChoice: required` on step 0). | Adopted | Found in the first live run: the fallback model answered "latest news" from stale knowledge and invented citations 1 to 5. The gate dropped them, but the stale answer still went out. This does **not** force search in general; whether to search stays the model's call. A stale answer with *no* citations is not caught (the eval's fresh-fact cases are the check). | Forcing search on every question that sounds fresh; leaving it to the prompt |
| I19 | If a provider says the request was **too large**, retry the same model once with half the evidence, before using the fallback model. | Adopted | A prompt-size problem is ours to fix; switching models would change answer quality for no reason. Test: `retries the same model with half the evidence`. | Falling straight to the fallback |
| I20 | **Finding: Groq's free tier (8,000 tokens/minute on `gpt-oss-120b`) cannot sustain multi-round agent turns.** Each step re-sends the whole conversation, so one three-call turn is about 8k input tokens and a second turn within the minute is rate-limited. Mitigations: SDK retries raised to 4 (it waits the provider's "try again in Ns"), the answer fallback model, small budgets. Not a fix: for development, prefer a model with a large limit (Gemini's free tier) as primary, or Groq's Dev tier. The benchmark should report this honestly. | Adopted | Measured, not assumed. | Treating it as a bug in the agent |
| I21 | **Instruction-leak guard in code.** A reply sharing two or more distinct 5-word runs with the system prompt (identity line excluded) is replaced with a fixed refusal, and a trace warning is recorded. A prompt rule on self-description backs it up. | Adopted | A user got the assistant to quote its prompt and invent details about itself. A prompt rule alone can be talked around; this check cannot. Limits: verbatim only, and streamed text can show briefly before the replacement. | Prompt rule only; a keyword blocklist |
| I22 | **The assistant does not say which model, vendor or architecture it runs on.** It says it cannot share that. | Adopted | It cannot reliably know, and in the first report it invented "GPT-4-Turbo". "I can't share that" is honest; a guess is not. | Telling the model its own name |
| I23 | Progress, findings and measurements are kept in `docs/PROGRESS.md`. | Decided (you asked for it) | One place that separates what was built from what was measured from what is still unproven. | Scattering notes across chat |
| I24 | **Exa added as a second search backend, not a replacement.** `SEARCH_PROVIDER=tavily\|exa` picks the primary; if both keys are set the other is an automatic failover (`FailoverSearch`). `npm run bench -- --search exa\|tavily` compares them with separate fixtures. | Adopted (Tavily stays default until measured) | Evidence for "Exa tops search" is mixed and mostly vendor-run: Openbenchmarks (independent) measured Exa Instant at about 398 ms vs Tavily Basic at 1.88 s mean latency; one vendor-run BrowseComp report had Exa 33.7% vs Tavily 19.3% accuracy, with Brave and Parallel ahead of both; AIMultiple put Exa in the top four and Tavily fifth of eight. None of that is our workload. Exa also fits the architecture: one call returns query-relevant highlights and, for `depth: read`, page text, so the pipeline skips its own fetch. Free tier: $10 monthly credit (about 2,500 Lite searches), no card; `auto` $7 per 1k searches. Unverified live: the adapter is unit-tested against the documented request/response shape only. | Replacing Tavily outright on a headline claim |
| I25 | **Web and API are separate apps on separate ports.** API on :8000 (`PORT`), web on :5173 (dev) / :4173 (preview). The API no longer serves `web/dist`; Vite proxies `/api` to it (target follows `PORT` from `.env`), and the API also sends CORS headers for `WEB_ORIGIN` so a separately hosted UI can call it directly. | Adopted | One origin on one port hid the boundary and made the build output part of the API's job. Separate processes match how it would be deployed (static host + API) and keep each side restartable on its own. | The API serving the built UI (convenient, but couples deploys and blurs ownership) |
| I26 | **Frontend moved to Tailwind v4 with a feature-based layout.** `web/src/{pages,components/{ui,chat,benchmark},hooks,lib,styles}`, `@/` import alias, `react-router` for `/` and `/benchmark`, chat logic in a `useChat` hook, theme tokens as CSS variables mapped to Tailwind colours in one place. | Adopted | A single 1,000-line global stylesheet leaked rules between screens (a chat `.warn` rule broke the benchmark cards). Scoped utilities plus a small token layer remove that class of bug, and separating data logic from components makes each piece testable and replaceable. | Hand-written global CSS; CSS modules (more files for the same result) |
| I27 | **Conversational voice and clarification live in the system prompt.** New `# Voice` and `# When the question is unclear` sections: match the user's register, short human replies to thanks and greetings (one line, under 20 words), use what is known about the user sparingly, no stock closers or flattery, ask one question only when a wrong guess would waste the user's time, otherwise state the assumption and answer. | Adopted | Plain Q&A felt bland. Probed live: greeting by name with one useful question, one-line replies to "thanks", a clarifying question for "Mercury". A first version let "thanks, that helps" through with a long reply and a stock closer; adding a concrete length rule fixed it. | Persona via a second rewrite pass (extra latency and cost for every answer) |
| I28 | **Stale-answer guard in code.** If a question matches a time-sensitive pattern (latest, current, price, news, scores, weather, who is the current ...) and the model answered with no search at all, the harness re-runs once with `toolChoice: required`. Recall questions about earlier chats are exempt. | Adopted | The earlier guard only caught answers that cited sources they never retrieved. An uncited stale answer ("the latest Node is v22") passed silently. A false positive costs one search; a false negative ships a wrong answer. | Trusting the prompt alone |
| I29 | **Follow-up chips come from a separate endpoint.** `POST /api/suggest` runs the background model after the answer is done; failures return no chips. | Adopted | The answer must never wait on a nice-to-have, and the chat stream stays one concern. | Emitting suggestions on the chat stream (delays `done`) |
| I30 | **Memory is inspectable and removable.** `DELETE /api/memory/facts/:id` and `/claims/:id`; recorded facts show "changed, was X (date)" using the superseded claim. | Adopted | Remembering things about a person needs a visible way to forget them. | Read-only memory view |
| I31 | **Snippets of 9+ characters are kept as evidence** (was 21+). | Adopted | A test with the snippet "Node 26.1 released." was silently dropped, so the hit never became a source. Short release-note snippets are exactly the facts that matter. | Keeping the old threshold |
| I32 | **Page fetcher resolves DNS and re-checks every redirect.** `isPublicUrl` rejects any hostname that resolves to a private, loopback, link-local, CGNAT or multicast address (IPv4, IPv6, IPv4-mapped); redirects are followed by hand (max 5) and each hop is validated. | Adopted | A syntactic hostname check let a public-looking name resolve to an internal address, and a public page could redirect the fetcher to `169.254.169.254`. Found along the way: Readability empties the DOM, so the plain-text fallback never worked; it now runs first. | Hostname blocklist only |
| I33 | **Reasoning effort is a per-model, opt-in setting** (`ANSWER_REASONING=low\|medium\|high`). Sent as `reasoningEffort` for Groq gpt-oss and `thinkingBudget` for Gemini 2.5 only; other models are left at default. | Adopted, off by default | Reasoning tokens are usually the largest part of time-to-first-token, so this is the first lever to benchmark. | I34 | **Speculative pre-fetch** (`SPECULATIVE_SEARCH=1`): for time-sensitive questions, search once before the first model call and put the evidence in that call. | Adopted, off by default | Removes one model round trip (and its tokens) when the model would search anyway. Costs a search credit when the question did not need one. Keep only if a benchmark shows lower time-to-first-token without hurting pass rate. | Always on; running the search in parallel with the model (cannot put evidence in the first call) |
| I35 | **Light stemming in passage ranking.** "release / releases / released / releasing" and "price / prices / pricing" share a bucket. | Adopted | BM25 on exact tokens missed inflections, so a passage could rank at zero for a query that obviously matched. | I36 | **History is token-budgeted.** The newest exchange is kept in full; older turns are trimmed harder and dropped past `HISTORY_TOKEN_BUDGET` (1800); dropped turns are covered by episode summaries. | Adopted | Ten full messages of up to 4,000 characters could exceed Groq's 8,000 tokens-per-minute limit on a long chat and made per-turn cost grow with chat length. | Fixed last-10 messages |
| I37 | **Cost per answer is opt-in.** `MODEL_PRICES` (USD per 1M tokens, by model spec) enables an estimate in Details; with no entry nothing is shown. | I38 | **Eval suite grew to 37 cases** (new: conversation, freshness guard, multilingual, more injection) and a CI-safe test checks every case is well-formed (unique ids, compiling regexes, consistent expectations). | Adopted; new cases not yet run live | The suite is code too. The 11 new cases need a live run once model quota allows. | Waiting to add cases until they can be run |
| I39 | **Personal questions are answered like a person, and example wording is exempt from the leak guard.** The memory rules now say: if asked something about the user that is not in "what the user has told you", say they have not told you yet and ask; never mention chat dates or records. The "no record" wording applies only to past-date questions. The prompt carries one sanctioned example sentence, and the leak guard ignores indented `Say:` / `Instead of:` lines. | Adopted | "What is my name?" produced "I don't have a record of your name. The most recent chats I see are from 2 Nov 2026 ... Let me know how you'd like to proceed": accurate but robotic, and it surfaced irrelevant chat dates. First fix attempt made things worse: the guard saw the example wording in the prompt and replaced the correct answer with the refusal text; found by live probe, now covered by tests in both directions. | Leaving tone entirely to a general "be warm" rule |
| I40 | **Two paths: fast (one agent loop) and deep (plan → parallel researchers → synthesis → verifier).** A deterministic router picks per question; the composer has Auto / Fast / Deep. | Adopted | Most questions need one focused search, and speed is judged; hard questions (comparisons, multi-part, "research X") benefit from decomposition and are visibly better when the plan and progress are shown. | I41 | **The router is a cheap LLM classifier, with rules as the fallback.** The research model returns `{path, reason}` for the question plus the previous exchange (1 s, ~100 tokens, 4 s timeout); forced modes and tiny messages skip it; on timeout, rate limit or bad output the keyword rules decide. | Adopted (supersedes the rules-only first version) | Keywords miss paraphrase and other languages and misfire on words like "research" in a trivial question. Not yet measured against a labelled routing set. | Rules only; classifying inside the answer model's own call (couples routing to the answer model's quota) |

| I43 | **Claim verification against retrieved passages.** The registry keeps the passages shown to the model; a verifier lists cited claims their source does not support, and one rewrite removes or softens them. The citation gate still runs afterwards. | Adopted (deep path only; not yet measured) | The old gate proved a citation exists, not that it supports the claim, which is the most common real-world failure of cited answers. | I44 | **Research roles use a separate, cheap model** (`RESEARCH_MODEL`, default the background model); the answer model only writes the final synthesis. | Adopted | Planner, researchers and verifier are many short calls; putting them on the answer model would exhaust its per-minute budget (Groq free tier 8,000 TPM). | Everything on the answer model |
| I45 | **Per-user scoping lives in the store, not the routes.** `MemoryStore.forUser(id)` returns a view over the same database where every read and write on conversations, episodes, facts and claims is filtered by `user_id`. | I47 | **Rate limits are token buckets behind an interface, plus a concurrency cap.** Chat 12/min per user (3x per IP), API 240/min, sessions 20/min per IP, 2 answers streaming per user, 64 KB request bodies; 429 with `Retry-After` and a human message that the UI shows. | Adopted | One turn can fan out into many model and search calls, so unlimited requests are a cost and availability hole. | I52 | **A turn is a durable run, decoupled from the HTTP request.** A `RunManager` executes each turn on its own abort signal; a `runs` row records `running`, `done`, `failed`, `stopped` or `interrupted`. | Adopted | Tying the turn to the connection meant a refresh, a flaky network or a closed tab aborted the work, wasted quota, and lost the answer. | I53 | **Resumable event stream.** Every event gets a sequence id; the log is in memory for a short time after the run ends. | I54 | **Crash recovery is honest, not magic.** At startup any run still `running` becomes `interrupted` with a plain explanation; the conversation endpoint returns the latest run, and the UI shows the unanswered question with Retry. | I55 | **Idempotent sends and explicit stop.** The client sends a request id; a repeat attaches to the existing run for free (no second user message, no allowance spent).
